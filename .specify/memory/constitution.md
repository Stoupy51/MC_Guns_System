# MC Guns System Constitution

## Core Principles

### I. Python Sources Are The Only Source Of Truth

Every datapack and resource pack file is generated by the beet pipeline declared in `beet.yml`.
Nothing under `build/` is ever hand-edited, and no `.mcfunction` or generated JSON is committed as a source file.
A behavior change means editing `src/`, rebuilding, and letting the pipeline emit the result.

### II. Data-Driven Definitions

Weapons, magazines, grenades, perks, traps, map elements and any other repeated entity are described as data, not as duplicated code.
Structured data is modeled with `@dataclass`, and tables are written as one explicit keyword-argument constructor call per row, never as tuples splatted through a comprehension.
When two systems differ only by values, they share one parameterised implementation.

### III. Typed, Linted, Readable

All Python passes pyright strict and `ruff check src --fix`, with no `Any`, no `# type: ignore`, and no `cast` used to silence an error.
Leading whitespace is tabs, column alignment is spaces, every name is public (no `_` prefix), and module-level helpers are grouped into classes with `@staticmethod`.
A file approaching 300 lines becomes a package grouped by feature, not by kind.

### IV. Runtime Cost Is A Design Constraint

The pack runs every tick on a live server, so entity selectors, NBT reads and per-tick scans are budgeted before a feature is written.
Prefer scoreboard state, tags, macro dispatch and scheduled work over repeated `@e` scans and `if entity` chains.
Any feature that adds per-tick work states what it costs and how it is gated.

### V. In-Game Verification

Correctness is proven by building the pack and playing it, not by unit tests alone.
Every task list ends with explicit in-game checks: the commands to run, the state to observe, and the failure mode to rule out.
A feature is not done until it has been exercised in Minecraft at the version pinned in `beet.yml`.

## Technology And Build Constraints

- Python `>=3.14`, dependencies managed with `uv` (`uv.lock` is authoritative, `package = false`).
- Build pipeline is StewBeet on top of beet, configured entirely in `beet.yml`. Pipeline order changes are deliberate and explained.
- Target Minecraft version and pack version live in `beet.yml` (`minecraft`, `version`). Code never hardcodes a second copy of them.
- Namespace is `mgs`. Assets live in `assets/`, third-party packs in `libs/` (merged through Smithed Weld), build artifacts in `build/`.
- Systems are modularized by domain under `src/functional/` (core, weapon, multiplayer, missions, zombies, map_editor, progression, helpers). A new system gets its own package.
- Map data is authored through the in-game editor as storage compounds with relative coordinates. Coordinates are never hardcoded in functions.

## Development Workflow

- Features follow the Spec Kit flow: `/speckit-constitution`, `/speckit-specify`, `/speckit-plan`, `/speckit-tasks`, `/speckit-implement`, with `/speckit-clarify` and `/speckit-analyze` used whenever a spec has open questions.
- Specs live in `specs/<feature>/` and are committed with the code they describe.
- Commits use conventional format with a gitmoji after the colon, for example `feat(zombies): ✨ Add juggernog perk`. Subject line plus at most a sentence or two.
- Commits happen on request only, and pushing is done by the maintainer.
- User-facing changes update `README.md` (feature matrix, mode lists, known WIP items) in the same change.

## Governance

This constitution takes precedence over habit and convenience.
Plans and task lists are checked against it before implementation, and any deliberate deviation is written down in the plan's complexity tracking with the reason it is worth the cost.
Amendments are made by editing this file, bumping the version, and noting what changed: MAJOR for removing or redefining a principle, MINOR for adding one or expanding a section, PATCH for wording.
